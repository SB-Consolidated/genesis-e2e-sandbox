## Change 1: Dependency Matrix & Parallel Execution

### Problem

**v0.9.4 Limitation:**
- Tickets assigned sequentially one at a time
- No formal dependency tracking
- Cannot execute independent tickets in parallel
- If Ticket-002 fails, dependent Ticket-003 may already be executing

### Solution

Add **DEPENDENCY-MATRIX.json** created by Coordinator after ticket generation:

```json
{
  "version": "1.0",
  "tickets": [
    {
      "id": "TICKET-001",
      "name": "Setup Database Schema",
      "dependencies": [],
      "type": "sequential"
    },
    {
      "id": "TICKET-002",
      "name": "Create User Model",
      "dependencies": ["TICKET-001"],
      "type": "sequential"
    },
    {
      "id": "TICKET-003",
      "name": "Create Product Model",
      "dependencies": ["TICKET-001"],
      "type": "parallel"
    },
    {
      "id": "TICKET-004",
      "name": "User-Product Relations",
      "dependencies": ["TICKET-002", "TICKET-003"],
      "type": "sequential"
    }
  ]
}
```

## Change 2: Escalation Directory & Founder Protocol

### Problem

**v0.9.4 Limitation:**
- Ambiguous when Coordinator should guide vs. escalate
- No formal protocol for Founder business/design decisions
- Informal escalation requests not tracked
- Coordinators may overstep authority boundaries

### Solution

Add **escalation/** directory for formal Founder decision protocol with **three-tier resolution:**

1. **Technical/Implementation** → Coordinator provides guidance
2. **Clarification/Specification** → Coordinator provides guidance
3. **Business/Design Decisions** → Coordinator escalates to Founder

**Scope Changes:**

## Change 3: ExecutionOrchestrator - 13 Atomic Micro-Steps

### Problem

**v0.9.4 Limitation:**
- Step 2 was monolithic with time-based polling
- No granular control over each sub-step
- Difficult to resume after failures
- Poor visibility into exact workflow state

### Solution

Complete rewrite as **ExecutionOrchestrator** with 13 atomic micro-steps and **file-based completion detection** (not time-based).

### 13 Micro-Steps Implemented

1. **Step 2.0:** Verify Environment & Ticket Inventory
2. **Step 2.0b:** Resolve Coordinator Blocker Issues
3. **Step 2.1:** Authorize Next Ticket(s)
4. **Step 2.2:** Prepare Context (with retry tracking)
5. **Step 2.3:** Invoke Execution Agent
6. **Step 2.4:** Poll for Completion Contract
7. **Step 2.5:** Validate Completion Contract
8. **Step 2.5b:** Request Coordinator Fix (invalid contract)
9. **Step 2.6:** Move to MERGE_READY
10. **Step 2.7:** Merge via Coordinator
11. **Step 2.8:** Move to COMPLETE
12. **Step 2.9:** Cleanup Authorization
13. **Smart Resume:** Process In-Progress Tickets

### File-Based Completion Detection

**Key Principle:** Files are state markers, not time

#### Completion Contract: CC-{ticket}.md
```
Location: Genesis Execution/contracts/completion/CC-TICKET-001.md
Indicates: Execution Agent finished implementation
Detection: File exists + Status: READY_FOR_REVIEW
Action: Proceed to validation (Step 2.5)
```

#### Issue File: {ticket}.issue.json
```
Location: Genesis Execution/issues/TICKET-001.issue.json
Indicates: Execution Agent encountered blocker
Detection: File exists
Action: Invoke Coordinator for guidance (Step 2.10)
```

#### Guidance File: {ticket}.guidance.json
```
Location: Genesis Execution/guidance/TICKET-001.guidance.json
Indicates: Coordinator provided resolution
Detection: File exists
Action: Retry Execution Agent with guidance (Step 2.13)
```

#### Merge Confirmation: MERGE-{ticket}.json
```
Location: Genesis Execution/contracts/completion/MERGE-TICKET-001.json
Indicates: Coordinator completed merge
Detection: File exists
Action: Proceed to move COMPLETE (Step 2.8)
```

#### Execution Context: execution-context-{ticket}.json
```
Location: Genesis Execution/contracts/completion/execution-context-TICKET-001.json
Contains: retry_count, guidance_path, contract_path
Purpose: Track retry state across restarts
Persists: Until ticket reaches COMPLETE
```

### Smart Resume Logic

**Problem:** System crashes/restarts mid-execution  
**Solution:** Use file artifacts to determine exact state

#### Resume Algorithm:
```
On Startup:
1. Check for tickets in 03_EXECUTING:
   For each:
     a. Check for issue file (Priority 1)
        → If exists: Handle via retry loop
     b. Check for contract file (Priority 2)
        → If exists: Agent finished, continue pipeline (validate→merge→complete)
     c. No files found
        → Execution interrupted, will re-execute in main loop

2. Check for tickets in 04_MERGE_READY:
   For each:
     a. Check for merge confirmation (MERGE-{ticket}.json)
        → If exists: Skip Coordinator, just move to COMPLETE
     b. No confirmation
        → Invoke Coordinator to merge

3. Context File Reuse:
   - If execution-context-{ticket}.json exists:
     → Read and preserve retry_count
     → Update paths/flags but keep retry state
   - If not exists:
     → Create fresh context
```

## Change 4: Smart Resume with Contract-Based State

### Problem

**v0.9.4 Limitation:**
- Time-based resume detection ("stale after 30 minutes")
- Couldn't distinguish between interrupted execution vs. completed execution
- Lost retry state across restarts
- Would re-invoke agents unnecessarily

### Solution

**Contract-based state detection** using file artifacts as deterministic markers.

### State Detection Priority

**For EXECUTING Tickets:**
```
Priority 1: Check for issue file → Problem found after execution
            Action: Handle via normal retry flow

Priority 2: Check for contract file → Agent finished execution
            Action: Resume from validation → merge → complete

Priority 3: No contract, no issue → Execution interrupted
            Action: Will re-execute in main loop
```

**For MERGE_READY Tickets:**
```
Priority 1: Check for MERGE-{ticket}.json → Already merged
            Action: Skip Coordinator, just move to COMPLETE

Priority 2: No confirmation → Not yet merged
            Action: Invoke Coordinator to merge
```

### Context File Reuse

**Problem:** Retry count lost on restart  
**Solution:** Preserve execution-context-{ticket}.json

```typescript
On Resume:
if (context file exists) {
  // Reuse existing context
  context = readContext()
  context.retry_count preserved  // Keep retry history
  context.guidance_path updated  // Update paths
  context.contract_path updated
} else {
  // Create fresh context
  context = createFreshContext()
  context.retry_count = 0
}
```

### Idempotent Operations

**Merge Operation (Step 2.7):**
```typescript
Before:
- Always delete MERGE-{ticket}.json
- Always invoke Coordinator
- Problem: Duplicate invocations on resume

After:
- Check if MERGE-{ticket}.json exists first
- If exists: Return true (already done)
- If not exists: Invoke Coordinator and poll
- Result: Safe to call multiple times
```

## Change 6: TICKET-NNN Naming Enforcement

### Problem

**v0.9.4 Issue:**
- Coordinator created tickets with wrong naming (ENGINE-0001 instead of TICKET-001)
- Caused completion detection to fail
- Batch processing stopped after first batch

### Solution

**Explicit naming requirements** in both ticket list and batch creation prompts.

### Naming Standard

**Format:** `TICKET-NNN` where NNN is 001-999

**Rules:**
- ✅ Correct: TICKET-001, TICKET-002, TICKET-999
- ❌ Wrong: ENGINE-001, TICKET-0001, Ticket-1, TASK-001

### Prompt Changes

#### Ticket List Creation:
```
CRITICAL ID FORMAT REQUIREMENTS:
- ALL ticket IDs MUST use prefix "TICKET-" (uppercase)
- ALL ticket IDs MUST use exactly 3 digits with leading zeros
- Correct: "TICKET-001", "TICKET-002", "TICKET-999"
- WRONG: "ENGINE-001", "TICKET-0001", "Ticket-1", "TASK-001"
- The ID format is TICKET-NNN where NNN is 001 through 999
```

#### Batch Creation:
```
CRITICAL FILENAME REQUIREMENTS:
- Filename MUST exactly match the ticket ID listed above
- Example: For ticket ID "TICKET-001", filename MUST be "TICKET-001.md"
- Example: For ticket ID "TICKET-002", filename MUST be "TICKET-002.md"
- DO NOT change the ID format (keep exact prefix and number format)
- DO NOT add extra text to filename (no "TICKET-001-description.md")
- Save to: Genesis Execution/tickets/01_DRAFT/[EXACT-ID-FROM-LIST].md
```

## Change 8: Phase 2 Screen Batching

### Problem

**v0.9.4 Limitation:**
- Step 0 says "generate ALL screens upfront" but no batching mechanism
- Strategy Agent receives one prompt and must generate everything at once
- **Result:** With large screen counts (10+ screens), Strategy Agent shortcuts with high-level summaries instead of detailed specifications
- Founder sees incomplete specifications lacking comprehensive detail

### Solution

Add **batch generation to Phase 2 Step 0** similar to Phase 5 ticket generation:

**Step 0a: Create Screen Index ONLY**
- Strategy Agent creates Screen-Index.md with list of ALL screens
- No folders created yet
- Stops after creating the index

**Step 0b: Generate Screen Batches (3 at a time)**
- Extension invokes Strategy Agent with batch of 3 screens
- Creates folders with Specification.md and Questions.md
- Polls for completion (both files must exist)
- Repeats until all screens generated

### Workflow Changes

#### Step 0a: Create Screen Index (NEW - Split from original Step 0)

**When:** User clicks "Generate All Screens" in Phase 2  
**Who:** Strategy Agent  
**Output:** `Genesis Execution/specs/UX Specs/Screen-Index.md`

**Process:**
1. Strategy Agent reads Phase 1 Strategic Directive
2. Identifies ALL primary screens needed
3. Creates Screen-Index.md with canonical checklist format
4. **STOPS - Does not create any folders**

**Screen-Index.md Format:**
```markdown
# UX Screens

## Active Screens

- [ ] Screen-001-Login
  Location: Genesis Execution/specs/UX Specs/Screen-001-Login/
  Status: Pending

- [ ] Screen-002-Dashboard
  Location: Genesis Execution/specs/UX Specs/Screen-002-Dashboard/
  Status: Pending

- [ ] Screen-003-Note-Editor
  Location: Genesis Execution/specs/UX Specs/Screen-003-Note-Editor/
  Status: Pending

## Archived Screens

(None)
```

**Completion Detection:**
- Extension polls for Screen-Index.md
- Parses file to extract screen list
- Proceeds to Step 0b

---

#### Step 0b: Generate Screen Batches (NEW - Split from original Step 0)

**Batch Size:** 3 screens at a time  
**Input:** Screen-Index.md (list of all screens)  
**Output:** Screen folders with Specification.md and Questions.md

**Batch Loop:**
```
Round 1: Generate Screen-001, Screen-002, Screen-003
  → Creates 3 folders with both files
  → Extension polls for completion
  → Updates Screen-Index.md: Status: Pending → Generated
  → Updates checkboxes: [ ] → [x]

Round 2: Generate Screen-004, Screen-005, Screen-006
  → Creates 3 folders with both files
  → Extension polls for completion
  → Updates Screen-Index.md status
  
Round 3: Generate Screen-007, Screen-008
  → Creates 2 folders with both files
  → All batches complete
```

**Completion Detection Per Batch:**
```typescript
// Both files must exist for each screen
function isBatchComplete(screenIds: string[]): boolean {
  for (const screenId of screenIds) {
    const specPath = `specs/UX Specs/${screenId}/Specification.md`;
    const questionsPath = `specs/UX Specs/${screenId}/Questions.md`;
    
    if (!fileExists(specPath) || !fileExists(questionsPath)) {
      return false;
    }
  }
  return true;
}
```

**Status Updates:**
- Screen-Index.md updated after each batch
- Status field: `Pending` → `Generating` → `Generated`
- Checkbox updated: `[ ]` → `[x]` when generated
